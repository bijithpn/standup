## Unified Engineering Rules

**Architecture**
* Maintain feature-first architecture (`lib/features/`).
* Respect layer boundaries (`core/`, `features/`, `shared/`).
* Prevent circular dependencies.
* Keep dependency direction inward towards the domain.
* Use strongly typed models.

**Dependency Injection**
* Register all dependencies only in `dependency_injection.dart`.
* No runtime business logic inside DI.
* No event wiring inside DI.

**State Management & Storage**
* Use Provider for local UI state.
* Use EventBus for cross-isolate and global app state synchronization.
* Repositories must act as the sole source of truth for persistence.
* Repositories must not open/close ObjectBox or use `SimplePrefs` directly (route through `StorageService`).

**UI & Widget Design**
* Avoid `BackdropFilter` for full-screen animations. Prefer gradient-based simulations.
* Pre-cache overlay assets.
* **Size Constraint:** No widget should exceed 300 lines without justification. Large widgets must be decomposed.
* Do not mix business logic and rendering.

**Services & IPC**
* Services must be interface-driven where appropriate, avoid UI dependencies, and remain platform-agnostic.
* IPC: No raw `Map<String, dynamic>` payloads or dynamic casting. Use strongly typed Freezed models and validate incoming payloads.

**Native Integrations**
* Use `FlutterEngineGroup` (`engineGroup.makeEngine`) for all secondary macOS windows.
* All permission flows require: Initial request, Denied state, Permanently denied state, Recovery path. No permission workflow is complete without all four.

**Error Handling & Security**
* Never throw generic `Exception`. Use `AppException` implementations.
* Route failures through `ErrorHandler`.
* Log recoverable and unrecoverable failures distinctively.
* Never store secrets in source code, never log sensitive information, and do not trust external IPC payloads without validation.

**Testing**
* Required before merge: Unit tests for business logic, Widget tests for critical UI, Native fallback tests, State transition tests.
* Critical modules must maintain: `TimerEngine` coverage, `TimerOrchestrator` coverage, IPC coverage.

**Performance**
* Avoid unbounded rebuilds and heavy work in `build()` methods. Minimize rebuild scope.
* Use `const` constructors wherever possible and cache assets appropriately.

**Comments**
* Explain Intent, Business rules, Platform behavior, Architectural decisions.
* **Do not explain obvious code.**
* No emojis, no AI-generated wording, no marketing language, no tutorial-style comments, no autogenerated headers.

## graphify

This project has a knowledge graph at `graphify-out/`. For codebase, architecture, or dependency questions, when `graphify-out/graph.json` exists, first run `graphify query "<question>"` (or `graphify path "<A>" "<B>"` / `graphify explain "<concept>"`). These return a scoped subgraph, usually much smaller than `GRAPH_REPORT.md` or raw grep output. Read `GRAPH_REPORT.md` only for broad architecture review or when those commands do not surface enough context.
